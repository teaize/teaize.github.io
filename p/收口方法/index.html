收口方法

我们用日常生活中最常见的「网购下单」来打个比方。

下单这件事底层其实非常繁琐，涉及很多步骤：

  1. 检查库存够不够
  2. 计算用户有没有优惠券
  3. 扣除账户余额
  4. 扣减真实库存
  5. 生成物流运单

没有收口方法（敞口状态）

如果系统没有提供“收口方法”，各个端的开发人员（比如写 App 界面的前端工程师）就得自己在界面代码里一步步去协调这些底层服务：

// ❌ 敞口设计：调用方必须自己知道所有细节、自己来回判断
async function handleUserClickBuyButton(userId: string, productId: string) {
  // 1. 自己查库存
  const stock = await stockService.check(productId);
  if (stock <= 0) return alert("库存不足");

  // 2. 自己查优惠
  const coupon = await couponService.findBestCoupon(userId, productId);
  const price = couponService.apply(productId, coupon);

  // 3. 自己去扣钱
  const payResult = await paymentService.deduct(userId, price);
  if (!payResult.success) return alert("扣款失败");

  // 4. 自己去扣库存
  await stockService.decrease(productId, 1);

  // 5. 自己去建物流单
  await deliveryService.createOrder(userId, productId);
}

问题在哪？

  • 前端写得要吐血：前端只是想实现“用户买了个东西”，却要关心 5 个服务的细节。
  • 极易出 Bug：如果明天老板说“下单前还要加一个【风控黑名单校验】”，那么 Web 端、iOS 端、安卓端、小程序端全部都得改一遍代码。

有了收口方法（收口设计）

// 服务的内部实现：把所有琐碎步骤收拢在里面
class OrderService {
  /**
   * 👉 这就是一个典型的【收口方法】
   * 外部只管调它，里面的库存、优惠、支付、物流细节全部内聚
   */
  async placeOrder(userId: string, productId: string): Promise<OrderResult> {
    // 内部自己按顺序调度：
    // 检查库存 -> 算优惠 -> 扣款 -> 扣库存 -> 创物流
    if (!this.checkStock(productId)) {
      return { success: false, reason: "库存不足" };
    }
    const price = this.calcDiscount(userId, productId);
    const paid = await this.pay(userId, price);
    if (!paid) {
      return { success: false, reason: "支付失败" };
    }
    const orderId = await this.createDelivery(userId, productId);
    return { success: true, orderId };
  }
}

// ✅ 收口后的调用：极简、稳定、无脑
async function handleUserClickBuyButton(userId: string, productId: string) {
  // 不管你内部有几百个流程，我只调这一个收口方法
  const result = await orderService.placeOrder(userId, productId);
  
  if (!result.success) {
    alert(result.reason);
  } else {
    alert("下单成功，单号：" + result.orderId);
  }
}

总结

用一句话概括就是：“化零为整，对外暴露一个总开关，对内按序调度一堆小开关。”

1. 软件设计模式：外观模式（Facade Pattern，门面模式）

这是你描述的场景在经典设计模式里最正统、最贴切的对应。

  • 概念：外部要与一个复杂的子系统（库存、优惠券、支付、物流）打交道。与其让外部面对十几张不同面孔的微服务，不如派出一个统一的“前台接待人员”（Facade，门面/收口）。
  • 类比：去医院看病，没有收口时你得自己跑挂号处、化验室、药房、缴费窗口（敞口）；有收口后，有了“一站式 VIP 导医服务”，你把医保卡交给导医，他帮你跑完所有窗口，最后把药给你。

2. 系统架构层：BFF 与 API 网关（Backend For Frontend / API Gateway）

当你把代码里的 OrderService.placeOrder 放大到整套网络架构时：

  • 网页端、iOS、安卓不需要分别向 5 台不同的微服务机器发 HTTP 请求。
  • 中间架设一台 API 网关或 BFF 服务，前端只发一个 POST /api/order/create 请求，网关在内网并行把子请求分发出去并汇总。这个网关就是物理网络层面的“收口服务”。

3. 面向对象原则：高内聚与封装（Encapsulation）

  • 收口的意义在于“隐藏易变的细节”：外部调用方只需要关心“业务意图”（我想下单），不需要关心“技术实现顺序”（先算优惠还是先查库存）。
  • 如果将来业务逻辑变更（比如加风控、把顺丰换成圆通），只有收口方法内部要改，成百上千个外部调用方毫无感知。

“收口”与“钩子”的有趣对比

维度 收口（Facade / 封装） 钩子（Hook / 反转）
动作方向 从外向内收（收敛） 从内向外放（开放）
核心目的 降低复杂度，隐藏细节，不让外部瞎操心 预留灵活性，暴露关键点，允许外部强行介入
形象类比 一键启动的“自动洗衣机总开关” 洗衣机运行中留的“中途添衣仓门”
