产品架构设计：功能、接口、依赖与约束

[!abstract] 核心观点 一个产品不仅仅是零部件、功能模块和软件程序的集合，更是一个与外部环境持续交互、依赖各种资源并受到多种条件约束的完整系统。

在设计一个产品时，应该优先回答四个核心问题：

  1. 功能（Function）：产品要完成什么任务？

  2. 接口（Interface）：产品与外部世界如何交互？

  3. 依赖（Dependency）：产品需要什么资源和条件才能实现功能？

  4. 约束（Constraint）：产品必须在什么边界条件下实现功能？

这四个问题构成了产品需求分析、系统架构设计、模块划分和设计评审的基础。

一、为什么需要从系统角度理解一个产品？

在传统的机械设计工作中，我们经常从零件和结构入手：

  • 需要什么零件？
  • 零件应该采用什么结构？
  • 尺寸应该如何确定？
  • 使用什么材料？
  • 如何加工和装配？

这些问题当然重要，但它们更多关注产品的具体实现。

如果在设计初期就直接进入零件建模，很容易忽略一个更重要的问题：

我们究竟要设计一个什么样的系统？

例如，设计一台自动化设备：

  • 它需要完成什么功能？
  • 它需要与哪些外部设备连接？
  • 它需要什么能源和物料才能运行？
  • 它需要满足什么环境和性能要求？

如果这些问题没有提前明确，后续可能出现：

  • 机械结构设计完成后，才发现安装接口不匹配。
  • 电气设计完成后，才发现供电容量不足。
  • 软件开发完成后，才发现通信协议不兼容。
  • 设备装配完成后，才发现维护空间不足。
  • 产品能够运行，但无法达到预期的精度和可靠性。

这些问题并不一定是零件设计错误，而可能是系统层面的需求和架构没有考虑完整。

因此，在正式设计之前，应该先建立产品的系统视角。

二、产品的四个核心问题

1. 功能（Function）：产品要完成什么任务？

功能描述的是产品存在的目的，以及它需要实现的能力。

它回答的是：用户为什么需要这个产品？这个产品究竟要做什么？

例如，一台自动化机械设备可能具有以下功能：

  • 自动输送物料。
  • 完成工件定位。
  • 对工件进行加工。
  • 自动检测加工结果。
  • 输出运行状态和故障信息。

功能分析需要关注产品最终要实现的结果，而不是过早限定具体实现方式。

例如：

需求：设备需要自动完成工件定位。

这是功能需求。

实现方式可能是：

  • 气缸推动定位。
  • 伺服电机驱动定位。
  • 电动推杆执行定位。
  • 机械凸轮实现定位。

这些属于不同的技术实现方案。

[!tip] 设计原则 先明确需要实现什么功能，再研究采用什么结构和技术实现。

不要在需求尚未明确时，就过早锁定具体的零件、结构或技术方案。

2. 接口（Interface）：产品与外部世界如何交互？

接口定义了产品与外部用户、设备或系统之间的交互边界。

它回答的是：

外部世界如何使用这个产品？产品如何与外部世界交换信息、能量和物质？

接口不只是一个连接器或者一个通信端口，而是一个更广泛的概念。

常见的接口类型包括：

接口类别 典型内容
机械接口 安装孔位、法兰尺寸、定位基准、连接方式
电气接口 电源电压、功率、接线端子、信号电平
通信接口 RS485、Modbus RTU、以太网、通信协议
控制接口 启停、复位、运行模式、设定值
数据接口 测量数据、运行状态、故障代码
人机接口 按钮、指示灯、触摸屏、操作方式
性能接口 精度、处理能力、响应时间、输出能力

接口设计的关键，不仅是明确接口的类型，还要定义接口的具体规格。

例如，一个 RS485 通信接口，至少还需要考虑：

  • 通信速率。
  • 数据位、停止位和校验位。
  • 通信协议。
  • 寄存器地址和数据格式。
  • 主从站关系。
  • 超时和异常处理机制。

同样，一个机械安装接口也不能只写明采用法兰连接，还需要明确法兰尺寸、孔位、定位方式、密封要求和承载能力。

[!important] 核心认知 接口定义了产品的边界，也决定了产品能否顺利融入更大的系统。

一个产品内部设计得再优秀，如果无法与外部系统正确连接和协作，也无法真正发挥价值。

3. 依赖（Dependency）：产品需要什么资源和条件？

依赖描述的是产品为了实现自身功能，需要哪些内部资源、外部资源和运行条件。

它回答的是：为了让产品正常工作，我们必须提供什么？

常见的依赖可以分为以下几类：

依赖类别 典型内容
能源依赖 220V AC、24V DC、压缩空气、液压动力
机械依赖 电机、减速机、轴承、导轨、紧固件
感知依赖 温度传感器、压力传感器、位置传感器
执行依赖 电磁阀、气缸、伺服电机、执行机构
控制依赖 PLC、控制器、驱动器
软件依赖 控制程序、通信驱动、算法、运行环境
环境依赖 工作温度、湿度、粉尘条件、安装环境
维护依赖 易损件、备件、维修空间、校准工具
外部系统依赖 上位机、数据库、网络、其他设备

这里需要特别注意：

依赖不一定都是产品内部的组成部分。

例如，一台设备可能需要外部提供：

  • 稳定的电源。
  • 一定压力范围的压缩空气。
  • 上位机通信连接。
  • 特定规格的原材料。
  • 定期校准和维护服务。

这些虽然不属于设备本体，但它们是设备能够正常工作的必要条件。

因此，产品设计不能只考虑设备本身，还必须考虑设备所处的运行环境和外部资源体系。

[!warning] 容易忽略的问题 产品设计时，不能只问需要安装哪些零部件，还要问这些零部件依赖什么才能正常工作。

例如，电磁阀依赖供电和气源，PLC 依赖供电和程序，通信模块依赖网络或总线连接。

如果只考虑第一层组成，而忽略更深层的依赖，就容易遗漏系统运行所需的条件。

4. 约束（Constraint）：产品必须在什么边界条件下实现功能？

约束描述的是产品设计和运行过程中必须遵守的限制条件。

它回答的是：产品必须在什么条件下工作？哪些事情不能超出允许范围？

常见约束包括：

约束类别 典型内容
尺寸约束 长度、宽度、高度、安装空间
重量约束 整机重量、单个模块重量
成本约束 研发成本、制造成本、维护成本
性能约束 精度、速度、响应时间、处理能力
能耗约束 功率、耗电量、气体消耗量
环境约束 温度、湿度、粉尘、腐蚀性环境
安全约束 防护等级、防爆要求、机械安全
标准约束 国家标准、行业标准、企业标准
可靠性约束 使用寿命、故障率、维护周期

例如：设计一台工业分析仪器，可能需要满足：

  • 环境温度：5～40℃。
  • 供电电压：AC 220V。
  • 整机功率：不超过某个设计上限。
  • 设备防护等级：满足安装场所要求。
  • 测量精度：满足相应技术指标。
  • 连续运行时间：满足现场运行要求。

约束与功能有明显区别。

功能是希望产品实现什么，约束是实现这些功能时必须遵守什么条件。

例如：

  • 功能：设备能够连续测量烟气中的 NOx 浓度。
  • 约束：设备需要在规定的环境温度范围内工作，并满足测量精度、响应时间和功耗要求。

[!tip] 核心认知 功能决定产品要做什么，约束决定产品必须在什么边界内完成这些事情。

一个功能能够实现，并不意味着产品就满足设计要求。

三、四个维度之间的关系

四个维度不是彼此孤立的，它们之间存在紧密的逻辑关系。

可以将其理解为：

  1. 功能定义产品需要实现的目标。
  2. 接口定义产品如何与外部世界交互。
  3. 依赖定义产品实现功能所需要的资源。
  4. 约束定义产品实现功能时必须遵守的边界。

例如：

一台自动化设备需要完成工件自动定位。

维度 对应设计内容
功能 自动完成工件定位
接口 工件入口、定位基准、电源接口、PLC 控制接口
依赖 气缸、气源、电磁阀、位置传感器、PLC
约束 定位精度、定位时间、设备尺寸、气源压力、安全要求

这四个维度可以组合成一个完整的产品分析模型：

flowchart TD A["产品系统分析"] A --> B["功能 Function
产品要完成什么任务？"] A --> C["接口 Interface
产品如何与外部交互？"] A --> D["依赖 Dependency
产品需要什么资源？"] A --> E["约束 Constraint
产品必须遵守什么边界？"] B --> F["产品需求与能力定义"] C --> F D --> F E --> F F --> G["系统架构设计"] G --> H["模块划分与技术方案"] H --> I["详细设计与实现"]

四、用 CEMS 系统理解四个维度

以一套 CEMS（连续排放监测系统）为例，可以更直观地理解这四个维度如何应用到真实产品中。

1. 系统功能

CEMS 的主要功能包括：

  • 采集烟气样品。
  • 对样气进行预处理。
  • 测量污染物浓度。
  • 测量烟气温度、压力、流速、湿度等参数。
  • 计算和处理监测数据。
  • 输出监测结果和设备运行状态。

2. 系统接口

接口类别 具体内容
烟气接口 烟道采样口、采样探头
气路接口 采样管路、标准气体入口、排气口
电气接口 AC 220V、DC 24V
通信接口 RS485、以太网
控制接口 设备启停、反吹控制、报警信号
数据接口 NOx、SO2、O2、流速、温度、压力等数据

3. 系统依赖

依赖类别 具体内容
能源 稳定的电源
气源 仪表空气、反吹气源
标准物质 标准气体、校准气体
采样系统 探头、伴热管线、采样泵
预处理系统 过滤器、冷凝器、排水装置
分析系统 分析仪、检测器、光学系统
控制系统 PLC、传感器、执行器
数据系统 数采仪、上位机、通信网络

4. 系统约束

约束类别 具体内容
测量性能 测量范围、准确度、响应时间
环境条件 烟气温度、环境温度、湿度
安装条件 采样位置、安装空间、维护空间
运行要求 连续运行能力、设备可用率
合规要求 适用的环保监测标准和技术规范
维护要求 校准周期、反吹周期、耗材更换周期

从这个案例可以看出：

CEMS 并不是简单地将采样探头、伴热管线、预处理设备和分析仪组合在一起。

它是一个由多个子系统组成的完整产品，各子系统之间存在明确的功能分工、接口关系、资源依赖和运行约束。

只有把这些关系梳理清楚，才能真正完成系统层面的设计。

五、从产品分析进一步走向模块化设计

理解四个维度之后，还可以进一步应用到模块化设计。

模块化设计并不是简单地把产品拆分成几个零件或几个功能区域。

真正的模块化设计，需要明确每个模块的职责，以及它与其他模块之间的关系。

对于每个模块，都应该回答以下问题：

分析维度 需要明确的内容
模块功能 这个模块负责完成什么任务？
输入接口 需要接收什么物质、能量或信息？
输出接口 向其他模块提供什么物质、能量或信息？
内部依赖 模块内部由哪些零部件和资源组成？
外部依赖 模块需要其他模块提供什么条件？
设计约束 模块需要满足什么尺寸、性能和环境要求？
异常处理 输入中断、依赖失效或输出异常时如何处理？

例如，一个 CEMS 预处理模块：

项目 具体内容
功能 将采集的样气处理到满足分析仪要求的状态
输入接口 原始样气入口、电源接口
输出接口 处理后的样气出口、排水口、状态信号
内部依赖 冷凝器、过滤器、蠕动泵、温度传感器
外部依赖 采样系统、供电、分析仪
约束 样气流量、露点、压力、温度、维护要求
异常处理 排水异常、温度异常、流量不足、过滤器堵塞时的检测和处理

这张表可以作为模块设计说明书的基础。

它还能帮助我们发现模块之间的接口是否完整、依赖是否遗漏，以及设计约束是否明确。

六、一个容易忽略的维度：异常与失效

在完成正常工作条件下的功能、接口、依赖和约束分析后，还应该进一步考虑异常情况。

因为一个产品真正的可靠性，不仅体现在正常情况下能够工作，还体现在异常发生时能够正确响应。

例如，一台自动化设备：

异常场景 需要考虑的问题
电源中断 设备如何停机？是否需要保存状态？
气源压力不足 能否检测？是否禁止执行动作？
通信中断 是否进入安全状态？如何恢复通信？
传感器故障 如何识别异常数据？是否需要报警？
执行器卡滞 如何检测动作失败？是否停止后续流程？
关键零件损坏 是否会引发连锁故障？如何保护其他部件？

这里涉及系统工程中的可靠性、安全性和故障分析。

尤其需要注意依赖之间的关系：

一个模块可能依赖多个资源，而一个资源也可能同时被多个模块依赖。

如果某个公共资源失效，就可能影响多个模块。

例如，24V DC 电源同时为 PLC、传感器和电磁阀供电，一旦电源故障，可能导致整个控制系统失去正常工作能力。

因此，产品设计不仅要梳理依赖，还要识别关键依赖、公共依赖和单点失效风险。

七、建立自己的产品分析工作流

以后面对一个新的产品或设备，不妨先建立一份产品分析表，而不是直接开始建模或编写程序。

产品系统分析表

分析项目 核心问题 输出成果
功能分析 产品要完成什么任务？ 功能需求清单
输入分析 产品需要接收什么？ 输入清单
输出分析 产品需要提供什么？ 输出清单
接口分析 产品如何与外部系统连接？ 接口控制文件 ICD
依赖分析 产品需要什么资源和条件？ 资源与依赖清单
约束分析 产品受到哪些边界条件限制？ 设计约束清单
异常分析 依赖失效或接口异常时怎么办？ 异常处理要求
架构设计 如何划分模块并组织关系？ 系统架构图

推荐的设计顺序

flowchart TD A["明确产品目标"] B["功能分析"] C["输入与输出分析"] D["接口分析"] E["依赖分析"] F["约束分析"] G["异常与失效分析"] H["系统架构设计"] I["模块划分"] J["详细设计与验证"] A --> B --> C --> D D --> E --> F --> G G --> H --> I --> J

这并不是一条绝对线性的流程。实际工程中，功能、接口、依赖和约束往往需要反复迭代。

例如，发现某个机械接口无法满足安装空间约束，就可能需要调整总体方案；调整方案后，又可能改变能源需求和其他模块的接口。

因此，系统设计本质上是一个不断分析、权衡、验证和迭代的过程。

八、最终认知：从零件设计思维走向系统设计思维

回顾整个思路，可以发现两种不同的设计视角。

传统的零件设计视角：

  • 这个零件怎么做？
  • 需要什么材料？
  • 尺寸应该是多少？
  • 如何加工和装配？

系统工程视角：

  • 产品需要完成什么功能？
  • 产品如何与外部世界交互？
  • 产品依赖什么资源才能运行？
  • 产品受到什么条件和边界限制？
  • 各个模块之间如何协作？
  • 当某个接口或依赖失效时，系统会发生什么？

两种视角并不矛盾。

零件设计解决具体实现问题，系统设计解决整体组织与协同问题。一个优秀的产品既需要可靠的零件设计，也需要合理的系统架构。

[!important] 最值得记住的一句话 不要一开始就问产品由什么零件组成，而应该先问产品要完成什么功能、如何与外部交互、依赖什么资源，以及受到什么约束。

当这四个问题回答清楚之后，产品应该如何划分模块、采用什么技术方案、选择什么零部件，才有了更加明确的设计依据。

延伸学习

  • 系统工程（Systems Engineering）：如何从整体角度组织复杂产品的需求、架构和验证？
  • 需求工程（Requirements Engineering）：如何将模糊的产品需求转化为可验证的技术指标？
  • 接口控制文件（ICD）：如何规范不同模块和设备之间的机械、电气、通信接口？
  • 功能架构与逻辑架构：如何从功能分解逐步形成系统模块？
  • 依赖分析与故障树分析（FTA）：如何识别关键依赖和单点失效？
  • 失效模式与影响分析（FMEA）：如何提前识别产品设计和运行过程中的潜在风险？
  • V 模型开发流程：如何将需求、系统设计、详细设计与验证测试对应起来？
